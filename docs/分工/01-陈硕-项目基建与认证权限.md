## 3. 第 2 周：认证接口（routers/auth.py，7 个端点）

### 3.1 GET /auth/captcha
- 函数：`get_captcha()`
- 逻辑：`generate_captcha(4)` → `uuid4().hex` 作为 key → `redis.setex(KEY_CAPTCHA.format(key=key), 300, code.upper())` → 返回 `{key, image}`（image 为 data URI）。
- 验收：`code(data["key"], data["image"])`；Redis 里存在 `captcha:{key}`，TTL ≤ 300。

### 3.2 POST /auth/register
- 函数：`register(body, request, db)`
- 入参：`{username, password, real_name?, phone?}`
- 逻辑：username 查重**不排除软删用户**（否则重名会撞唯一索引 500）→ `hash_password` → 建 `User(status=1)` → flush 拿 id → 绑 user 角色 → `log_op("register")` → 返回 `{id}`。
- 错误：10006 用户名已存在。
- 验收：注册成功 → 用新账号直接登录成功，前端菜单只有普通用户权限。

### 3.3 POST /auth/login（全项目最关键接口）
- 函数：`login(body, request, db)`
- 入参：`{username, password, captcha_key, captcha_code}`
- 流程（必须按顺序）：
  1. `_check_login_lock(redis, username, ip)`：账号或 IP 在 `login:lock:*` 里 → 直接 10005（429）；
  2. **Lua 原子取出即销毁**验证码：脚本 `GET` 后 `DEL`，比对 `captcha_code.upper()`，不匹配 → `_record_login_fail`（计数 +1 且**无条件** `expire` 600s；达到 5 次写 lock 并抛 10005）→ 再抛 10004；
  3. 查用户（含软删校验）→ `verify_password`；用户不存在或密码错 → `_record_login_fail` → 10002；status != 1 → 10007；
  4. 成功：清 `login:fail:{username}` 与 `login:fail:ip:{ip}` → `create_access_token` → `get_user_role_code` + `get_user_menus` → `log_op("login")`；
  5. 返回：
     ```json
     {"code":0,"message":"登录成功","data":{"token":"...","user":{"id":1,"username":"admin","real_name":"系统管理员"},"role":"admin","menus":[{"id":1,"name":"系统管理","menu_type":0,"children":[...]}]}}
     ```
- 验收：正确账号返回 token+role+menus；错误验证码 10004；连错 5 次 10005；锁期内正确密码也拒绝。

### 3.4 POST /auth/logout
- 函数：`logout(request, current_user, db)`
- 逻辑：从 `request.state.token` 取当前 token → `decode_access_token` 得到剩余有效期 → `setex(KEY_TOKEN_BLACKLIST.format(token=token), 剩余秒, "1")` → `log_op("logout")`。
- 验收：登出后拿旧 token 调 `/auth/profile` 必得 10001（401）。

### 3.5 PUT /auth/password
- 函数：`change_password(body, request, current_user, db)`
- 入参：`{old_password, new_password}`
- 逻辑：校验旧密码（错→10008）→ 更新 hash → 写 `KEY_PWD_FLOOR.format(user_id)` = 当前时间戳（TTL = JWT 有效期）→ `log_op`。
- 效果：`get_current_user` 拒绝 `iat` 早于改密时间的旧 token，**改密即全端下线**。
- 验收：改密后旧 token 401，新密码可重新登录。

### 3.6 GET /auth/profile、PUT /auth/profile
- `profile()`：返回当前用户信息 + role + menus（前端登录后再次刷新菜单用）。
- `update_profile(body, ...)`：仅允许改 real_name / phone / email，`log_op` 到本人名下。
- 验收：改姓名后重新登录显示新姓名；无 token 访问 401。

## 9. 常见坑位与修复约定（我这块血泪史）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 登录/鉴权偶发阻塞到超时 | Redis 挂起时连接无超时 | 连接池 `socket_timeout=3` |
| 2 | redis-py 8 报 HELLO 不支持 | 客户端默认 RESP3，Redis 5 不支持 | 连接池 `protocol=2` |
| 3 | 同秒多次签发 token 完全相同 | JWT iat 秒级精度 | payload 加唯一 `jti` |
| 4 | 验证码可重放 | GET 后 DEL 非原子 | Lua `GET+DEL` 原子取出即销毁 |
| 5 | 登录失败计数键永存 | 只在 count==1 设置 TTL 有竞态 | 每次 incr 后无条件 `expire` |
| 6 | 改密后旧 token 还能用 | token 无版本概念 | 写 `token:pwd_floor:{uid}`，`get_current_user` 比对 iat |
| 7 | 注册重名 500 | username 有唯一索引，软删用户被排除后重名入库 | 查重不排除软删用户 |
| 8 | 管理端改用户信息日志记错人 | 用被改用户身份写日志 | 操作日志一律记管理员名下 |
| 9 | bcrypt/passlib 兼容报错 | passlib 与新 bcrypt 不兼容 | requirements 钉 `bcrypt==4.0.1` |
| 10 | 前端 user 角色直达后台页连弹 403 | 路由守卫只看登录态 | 按授权菜单路径集合拦截 |
