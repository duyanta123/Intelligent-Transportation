# 06 · 自动化检查与 CI 门禁

> 配套阅读：《00-分工总览.md》第 6.5 节（Git 协作与分批次交付）、`AGENTS.md` 第 5/6/8 节
> 远端仓库：`https://github.com/duyanta123/Intelligent-Transportation`　|　平台：GitHub Actions（`.github/workflows/`）
> 适用对象：全体 5 人；第 5 节的"一次性配置"由组长（陈硕）执行

## 1. 为什么加这一层

多人并行开发时，靠自觉守规范迟早会被"赶进度"冲掉：有人把 `.env` 一起提交、有人提交信息写"更新"、
有人改了表结构忘了同步文档、Windows 上生成的 `.bat` 带上 BOM 到别人机器上直接报错。
这些问题的共同点是**机器一秒钟就能判断**，所以统一交给 CI 做合并前的强制关口，人只负责写代码和评审设计。

对应到课程要求，CI 把《00-分工总览》第 6.5 节"每批必过门槛"从"自己跑一遍"变成"远程自动跑、不绿不许合"。

## 2. 检查项总览

| 层次 | 位置 | 检查内容 | 不通过时 | 触发时机 |
|---|---|---|---|---|
| 仓库卫生 | `.github/workflows/ci.yml` → `repo-guard` | 禁止入库路径（`.env`/`venv`/`node_modules`/`dist`/`uploads`/`*.onnx`/日志/缓存）、单文件 >5MB、硬编码密钥、`.bat` 编码（CRLF+无 BOM+`chcp 65001`+无重复回车）、`.gitattributes` 行尾策略是否还在、配置项与 `.env.example` 对账、提交信息格式 | 阻断合并 | 每次 PR、`main`/`feature/**` 推送 |
| 后端质量 | 同上 → `backend` | `ruff check .` + `pytest -q`（GitHub 起 MySQL 8.0 + Redis 5 容器，用独立测试库 `smart_traffic_test`） | 阻断合并 | 同上 |
| 前端质量 | 同上 → `frontend` | `npm ci` + `npm run lint` + `npm run test` + `npm run build` | 阻断合并 | 同上 |
| 汇总门禁 | 同上 → `ci-gate` | 汇总上面三个作业 | 阻断合并 | 同上 |
| 密钥泄露 | `.github/workflows/security.yml` → `secret-scan` | gitleaks 全历史扫描（配置见 `.gitleaks.toml`，模板/文档示例值已白名单） | 阻断合并（分支保护必选检查「密钥泄露扫描」） | 每次 PR、`main` 推送、每周一 06:00 定时 |
| 依赖漏洞 | 同上 → `dependency-audit` | `pip-audit` + `npm audit` | 只提示不阻断 | 同上 |
| 依赖升级 | `.github/dependabot.yml` | 每周一 09:30 提 pip / npm 升级 PR，每月提 Actions 升级 PR，提交信息同样走 `chore(deps)` 规范 | —— | 定时 |
| 评审指派 | `.github/CODEOWNERS` | 共享文件、`sql/`、`docs/`、`.github/` 改动自动请求组长评审 | —— | 每次 PR |
| PR 模板 | `.github/PULL_REQUEST_TEMPLATE.md` | 强制填写自检证据、影响面、回滚方式（对应 AGENTS.md 第 8 节完成定义） | —— | 每次开 PR |

**只需要记住一条**：PR 页面出现绿色的「CI 全部通过」与「密钥泄露扫描」才能合并 `main`（依赖漏洞审计只提示、不阻断）。

> 项目主体按批次提交，所以 `ci.yml` 里有一个 `detect` 作业：它检查 `backend/requirements.txt` 与
> `frontend/package.json` 是否存在。骨架阶段（远端只有本套自动化文件）缺失的那部分会显示为
> `skipped`，`CI 全部通过` 仍然是绿的；等对应批次合入 `main` 后，对应作业自动开始真正跑 lint/测试。

## 3. 本地怎么用（推之前先跑一遍，省得远程红叉）

```bash
# 每次提交前：秒级，只查仓库卫生 + 提交信息
python scripts/precheck.py --guard-only

# 每批收尾 / 准备开 PR：与 CI 同口径的四条命令一起跑（pytest 需本机 MySQL80 + Redis 已启动）
python scripts/precheck.py

# 只验证"检查规则本身还有效"（改了 ci_check.py 之后必跑）
python scripts/ci_check.py --self-test
```

`scripts/precheck.py` 逐项打印命令与结果，失败也会继续跑完剩余检查项（一次看到全部问题），
最后汇总通过/失败清单，修完再推。它和 CI 用的是同一套规则文件 `scripts/ci_check.py`，不存在"本地过了远程挂"的口径差。

## 4. 远端怎么用（PR 流程自动跑）

1. 成员推分支 → 开 PR 到 `main` → GitHub 自动触发「CI 门禁」+「安全扫描」；
2. PR 页面底部出现 CI 门禁的 4 个检查：`仓库卫生与提交规范`、`后端 lint + 测试`、`前端 lint + 测试 + 构建`、`CI 全部通过`；另有安全扫描的 `密钥泄露扫描`（依赖漏洞审计仅提示、不阻断）；
3. 全绿 + 组长评审通过 → 合并；任何一个红 → 点进去看日志里 `[FAIL]` 那几行，本地复现修完再推；
4. 每周一 06:00 定时跑一次安全扫描，即使没人提 PR 也能发现新爆出的依赖漏洞。

## 5. 一次性配置（组长执行，约 5 分钟）

### 5.1 先推送自动化骨架（只推这一部分）

顺序很重要：**先把门禁推上去，后面的批次才有人管**。骨架提交里只有
`.github/`、`.gitattributes`、`.gitleaks.toml`、`scripts/ci_check.py`、`scripts/precheck.py`、
`scripts/setup_remote.sh`、`scripts/remote-branch-protection.json` 和本文档，
**不含** `backend/`、`frontend/`、`sql/`、课程文档等项目主体。

```bash
# 1) 看一眼骨架提交里到底有什么（应只有自动化相关文件）
git log -1 --stat chore/ci-bootstrap

# 2) 先看远端现状（不推送、不改动本地）：
#    列出远端 main 的提交、远端独有文件、两侧同名但内容不同的文件
bash scripts/setup_remote.sh --inspect

# 3) 推送（脚本全程不使用 --force）
bash scripts/setup_remote.sh
```

脚本会按远端情况自动选择推送方式：

| 远端 `main` 状态 | 脚本行为 |
|---|---|
| 空仓库 | 骨架作为首个提交推送 |
| 已有提交（例如建仓时"测试仓库是否创建成功"留下的提交） | 把骨架接到远端提交之上再**快进推送**；远端历史与远端独有文件（如测试 `README.md`）都保留；同名文件以骨架版本为准 |
| 远端与骨架有共同历史、但远端不是骨架祖先（说明别人已在推进） | 拒绝推送并提示改走「开分支 + 提 PR」（不覆盖别人的工作） |
| 网络/凭据不可用 | 明确报错退出，不做任何改动 |

推送后 GitHub 会自动跑第一次「CI 门禁」：`repo-guard` 正常执行，后端/前端作业按 `skipped` 处理。

### 5.2 开启 Actions

仓库 → **Settings → Actions → General** → Allow all actions（默认已允许，确认即可）。
本套流水线**不需要配置任何 Secret**：CI 用的是临时容器的测试凭据；`security.yml` 用内置 `GITHUB_TOKEN`。

### 5.3 配 `main` 分支保护（关键一步，否则检查只是"提示"不是"门禁"）

> **2026-09-23 更新：保护已用「规则集（Rulesets）」配置并生效**。此后调整一律走
> **Settings → Rules → Rulesets → `main`**；下方的 classic 口径仅作存档备用，勿与规则集叠加。

**现行口径：规则集（Rulesets）**，enforcement 为 active、作用于默认分支：

| 规则 | 配置 |
|---|---|
| Require a pull request before merging | ✅（1 个批准，且所有评论线程解决后才能合并） |
| Require status checks to pass | ✅ 必选检查 **CI 全部通过** 和 **密钥泄露扫描**；strict 开启（PR 分支须先同步 main） |
| Block force pushes / Block branch deletions | ✅ |
| Bypass list | 空（管理员同样不能绕过） |

必选检查名与检查运行名必须逐字一致（含中文），两个检查都已在 `main` 上跑出过，可直接搜索添加。

**存档口径：classic 分支保护**（早期方案，`scripts/remote-branch-protection.json` 为其载荷）：

```bash
gh api -X PUT repos/duyanta123/Intelligent-Transportation/branches/main/protection \
  --input scripts/remote-branch-protection.json
```

> ⚠️ **私有仓库的限制**：GitHub 免费账号的**私有**仓库不支持分支保护（需要 Pro/Team）。
> 课程作业建议直接把仓库设为 **public**（免费且分支保护可用），或在答辩时说明"检查项已就绪、
> 由 `ci-gate` 与「密钥泄露扫描」共同把关，保护规则因账号套餐未开启"。

> `bash scripts/setup_remote.sh --protect` 是上面命令的封装（只开保护、不重推代码；必选检查需先在
> 仓库里出现过一次）。**规则集已生效，此模式平时不要再跑**，以免在同一分支叠出第二层保护。

### 5.4 确认协作权限与评审指派

1. **Settings → Collaborators** 添加其余 4 人（Write 权限）；
2. `.github/CODEOWNERS` 里目前把共享文件、`sql/`、`docs/`、`.github/` 指给了 `@duyanta123`；
   拿到每个成员的 GitHub 账号后，把对应模块的负责人改成本人账号，即可实现"谁改谁评审"的自动指派；
3. 若想让 CODEOWNERS 成为强制项，再回到 5.3 在规则集的 pull request 规则里打开
   "Require code owner review"（注意：只把组长列为 owner 时，组长自己的 PR 会被卡住，
   所以建议先补全其余成员的 CODEOWNERS 条目再开）。

## 6. 提交信息规范（CI 会拦）

格式固定为 `type(scope): 简体中文描述`，`type` 只认下面几种（与 `AGENTS.md` 第 5 节一致）：

| type | 用于 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(停车): 出场结算调用计费纯函数` |
| `fix` | 修 bug | `fix(违章): 车牌格式校验漏新能源 8 位` |
| `test` | 补测试 | `test(大屏): 缓存命中与降级用例` |
| `docs` | 文档 | `docs(分工): 更新协作文档` |
| `chore` | 脚手架/依赖/脚本 | `chore: 锁定后端依赖版本` |
| `refactor` | 重构（行为不变） | `refactor(路况): 抽出拥堵分级纯函数` |

会被 CI 拦下的写法：`更新代码`、`fix bug`、`feat 新增接口`（缺 `(scope):` 或描述）、`wip`。
合并产生的 `Merge pull request ...` 与 Dependabot 的 `chore(deps): ...` 已自动放行。

## 7. 常见红灯与自救

| 现象 | 原因 | 处理 |
|---|---|---|
| `仓库卫生与提交规范` 红，日志出现 `xxx：真实 .env 含密钥` | 本地 `.env` 被 `git add` 进去了 | `git rm --cached backend/.env` 后提交；`.env` 已在 `.gitignore` 中，注意别用 `git add -f` |
| 同上，出现 `命中 N 个超大文件` | 把模型/数据集/大截图塞进仓库 | 移出仓库，改为运行时下载或走文档说明；确需入库时在评审中说明并调整阈值 |
| 同上，出现 `xxx.bat：含 UTF-8 BOM` | 用记事本/VSCode 保存成了带 BOM | 另存为 "UTF-8 无 BOM"，行尾 CRLF（见 AGENTS.md 第 7 节实测结论） |
| 同上，出现 `xxx.bat：存在 CR CR LF` 或 `.gitattributes 缺少 *.bat text eol=crlf` | 行尾工具叠加转换（历史遗留），或有人删了行尾策略 | 保留 `.gitattributes` 的两行策略；`.bat` 用编辑器重写为纯 CRLF（仓库内按 LF 存储、检出为 CRLF，不用手动改） |
| 同上，出现 `配置项 XXX 已定义但未写入 .env.example` | 新加了配置项忘了同步模板 | 在 `backend/.env.example` 补一行（仅测试用的开关可加入脚本忽略名单） |
| `后端 lint + 测试` 红（ruff） | 本地没跑 lint | 本地 `ruff check .` 看行号改完再推（`ruff check --fix .` 可自动修一部分） |
| `后端 lint + 测试` 红（pytest） | 用例依赖了本机数据/时区/顺序 | CI 用的是空库 + 种子夹具，禁止依赖开发库里已有的数据；补充夹具或在 `conftest.py` 里造数 |
| `前端 lint + 测试 + 构建` 红（`npm ci` 失败） | 改了 `package.json` 但没提交 `package-lock.json` | 本地 `npm install` 后把 `package-lock.json` 一起提交 |
| `密钥泄露扫描` 红但确认是示例值 | 文档里的演示密钥被误判 | 在 `.gitleaks.toml` 的 `allowlist.paths` 里加该路径或具体规则，**不要直接删检查** |
| PR 里检查一直显示 pending | 分支保护勾了还没跑过的检查项 | 等首次 CI 跑完后重新勾选，或确认 PR 已触发工作流 |

## 8. 后续怎么扩展

1. **文件级新规则**（推荐，成本最低）：在 `scripts/ci_check.py` 加规则，同时在文件顶部的
   `SELF_TEST_*` 样本里加"必须被抓到的坏例子"和"必须放行的好例子"，本地与 CI 立即同步生效；
2. **新作业**：在 `.github/workflows/ci.yml` 里加 job，并把它加进 `ci-gate` 的 `needs` 列表，
   否则新检查不会影响「CI 全部通过」这个门禁；
3. **静态安全分析（可选，一键开启）**：仓库 → **Settings → Code security → Code scanning** →
   选择 GitHub 默认的 CodeQL 设置。公开仓库免费，开启后每个 PR 会多一项 CodeQL 检查（Python + TypeScript）；
   私有仓库需 GitHub Advanced Security 才可用，故本套流水线未默认包含；
4. 改动检查项后，同步更新本文档与 `docs/PROGRESS.md`（AGENTS.md 第 8 节要求）。

## 9. 与课程交付的对应

- 分工文档要求"每批一个可运行状态、每批必过门槛"→ 由 `ci-gate` + `backend` + `frontend` 三个作业自动执行；
- "共享文件必须走 PR 评审"→ 由 `CODEOWNERS` 自动指派 + 分支保护强制 1 人评审；
- "禁止提交 `.env`、密钥只从环境变量读"→ 由 `repo-guard` + gitleaks 双重把关；
- 答辩/报告素材：仓库 **Actions** 标签页可展示历史流水线（谁的分支、哪次提交、过了哪些检查），
  是"工程化与质量保障"部分最直观的证据。
